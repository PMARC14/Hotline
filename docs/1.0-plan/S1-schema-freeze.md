# Job S1: freeze the file formats for 1.0 (branch fix-s1-freeze)

Follow W-common-rules.md in this folder (it is the "W.md" the briefs mention). Run this job FIRST in the 1.0 wave and merge it before the feature jobs: it changes how every config file is read and written. New strings go right after `Bar_WidthCells` in each resx. Owner decision (2026-10-31): "make sure core settings are frozen going forward file format wise". From 1.0 on a file written by any 1.x must load in any later 1.x without loss, and a file written by a newer 1.x must not lose data when an older 1.x saves it. Pre-1.0 renames are free now (read the OLD names as aliases for a while, write only the new ones). Origin of the list: the Opus design review of the config files (HANDOFF "Before 1.0: schema freeze").

Decisions (implement all, verify each against the code first):
1. **Unknown keys survive a save**: settings.json, every connections/<id>.json, toolbar.json (top level, `style`, each override entry, each custom button) keep keys they do not know (and their comments are NOT promised; the `.bak` copy covers that). Carry unknown JSON nodes through read -> model -> write (JsonExtensionData / an `Extra` JsonObject on the models). Tests: a file with future keys round-trips through load + Settings save with the unknown keys intact in every file type; the toolbar editor preserves unknown keys on every edit.
2. **One version rule**: every file has `"version": N` (integer). settings.json: today `schemaVersion` 14 -> read `schemaVersion` as an alias, write `version`; toolbar.json already `version` 2; connection files and mcp.json get `version: 1` (written; absent = 1). Rules (put them in docs/configuration.md and a comment in the code): adding a key never bumps the version; renaming/removing/changing meaning bumps it and REQUIRES a one-way migration with a backup; a file with a version higher than the app knows is read leniently, never rewritten except by a user action in Settings (and then unknown keys are kept), and a notice says it was made by a newer Hotline. Normalize must stop stamping blindly: keep the file's own version unless a migration ran.
3. **Written-out defaults, no rewrite on load**: keep writing every key on a user save (discoverable files, owner preference "anything configurable should be in settings.json"), but loading must NEVER rewrite a file just because options are missing (remove the `HasMissingOptions` rewrite-on-load): missing keys are filled in memory and written at the next user-initiated save. Null and missing mean the same thing ("default") in every file; write one form (omit nulls everywhere).
4. **Connection files**: the file name is the id (`connections/<id>.json`); the `id` key inside is no longer written, and ignored on read if it matches, with a warning if it differs (file name wins). Keep the safe-file-name rule and collision rejection already built; moving a file by hand = renaming the connection (document: API keys are stored per id, so rename = re-enter key; or migrate the key on an in-app rename if trivial).
5. **App-written state out of config**: `.first-run-shown` and `general.supportReminder` (and anything else Hotline writes by itself, check `SettingsService.Update` callers) move to `state.json` in the data folder (`{ "version": 1, "firstRunShown": "<iso>", "supportReminder": ... }`), lenient reader like the others, unknown keys kept; migrate: if the old marker/setting exists, honour it once. `settings.json` then contains only user choices.
6. **One backup policy**: replace the schemes (`.bak`, `.bad`, `.old`, `.old2`, `.bak-<stamp>`, `<file>.<time>.bak`, `backups\reset-*`, `backups\import-*`) by one helper writing to `backups\<file>.<yyyyMMdd-HHmmss>[-n].<reason>` with reason one of `edit`, `reset`, `invalid`, `import`, `upgrade`; newest 10 per file; skipped when the file is byte-identical to what Hotline last wrote; the existing "no backup, no write" rule stays. Keep import's `backups\import-<time>\` folder if simpler (it holds many files) but name its files the same way. Update every caller (SettingsStore, ToolbarFile, McpConfig.SaveApproval, SettingsReset, SettingsPackageImport, agy permissions, the Settings save buttons' `FileArchive.KeepOld`), docs file table, TESTING.md, and remove dead code (`FileArchive` if unused).
7. **Renames before the freeze** (new names written, old names read as aliases, one release of overlap documented): `window.height` -> `window.minHeight`; `chat.defaultBackend` -> `chat.defaultConnection` (keep `chat.order`); toolbar `items` -> `bottom` (the shipped `top`/`bottom` pair). Do NOT rename anything else (units go in the documentation and the JSON schema descriptions, not in key names). Aliases keep a file written by today's build loading with no warning: build the test fixtures by SERIALIZING today's defaults (`new HotlineSettings()`, `ToolbarModel.Defaults.ToJson()`) BEFORE you change anything, with the pre-rename key names, and commit them as the old-alias fixtures (do not copy anyone's real files from ~/.hotline into the repo).
8. **JSON schema + compatibility suite**: ship `docs/schema/settings.schema.json`, `toolbar.schema.json`, `connection.schema.json`, `mcp.schema.json` (draft-07, descriptions with units and ranges, all current keys and enums, `$schema` allowed as an ignored key on read and left in place on write) generated from the code's key tables where practical; a test asserts every key the code reads appears in its schema and vice versa (so adding a key forces a schema + docs update). Add `tests/Hotline.Core.Tests/Compat/` with frozen fixtures per file type (a "1.0" file with every key, an old-alias file, a future-key file) and ONE test per file type that loads each fixture with zero problems, saves, reloads, and compares — these fixtures must never be edited after 1.0 (say so in a README in that folder).
9. Docs: rewrite the "Files" and per-file sections of docs/configuration.md around these rules ("Compatibility promise from 1.0"), TESTING.md, and list for HANDOFF what changed.

Report as W-common-rules.md says. This is the biggest job of the wave: commit per decision (1..9) so the controller can cherry-pick and review each.
