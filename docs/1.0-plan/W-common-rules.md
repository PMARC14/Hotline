# Common rules for the 1.0 jobs (Hotline repo)

You work ONLY in your own git worktree (the path and branch are in your prompt; the branch already exists at the right base). Never touch the main checkout C:\Users\pmadd\Git\hotline or other worktrees. Rules:
- Author pmarc14 <16502495+PMARC14@users.noreply.github.com> (already configured), no Co-Authored-By / "Generated with" lines. Never push, never merge, never touch other branches. Small logical commits.
- TDD in src/Hotline.Core: write the failing test first, then the code. Tests: `dotnet test --project tests/Hotline.Core.Tests/Hotline.Core.Tests.csproj` (whole suite green before every commit); build: `dotnet build Hotline.slnx` (must succeed, no new warnings in your files). The suite is large: new tests must be compact (Theory with InlineData / table-driven, shared helpers), not one Fact per case; do not copy-paste test files.
- Match the surrounding code (comment density, naming, idiom). Read docs/HANDOFF.md ("Hard-won facts"), docs/configuration.md and CLAUDE.md first.

- You may NOT run, install or start Hotline, open windows, use the clipboard or send keystrokes (the controller does UI verification); anything you cannot verify without the UI goes in your report.
- Heredoc quirk: write C#/scripts containing backslashes or `\n` escapes with the Edit/Write tools, not shell heredocs (they get collapsed); python run from bash cannot read `/tmp` paths: use paths under your worktree or the scratchpad.
- New user-visible strings: English in `src/Hotline.Core/Text/Localization/Strings.resx` AND the same English as a temporary placeholder in the 16 other `Strings.<lang>.resx`, each new `<data>` inserted right after the key named in your job (parallel jobs insert after different keys); `LocalizationTests` must pass. List every new key + English text in your report.
- Docs: update docs/configuration.md (formats/settings), docs/TESTING.md (a manual line per UI-side feature), README only if a feature list changes. Never edit docs/HANDOFF.md (list what it needs in your report).
- Final report (under 40 lines): what was built, per-item FIXED/DONE/DEFERRED with the test names, changed existing tests and why, new strings, what you could not verify without the UI, commit SHAs.
